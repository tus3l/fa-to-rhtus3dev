# TUS3dev

منصة عربية RTL لمستندات المشاريع والإقرارات الإلكترونية. الصفحة الرئيسية هي `index.html` وليست صفحة تسويقية. الواجهة HTML/CSS/JavaScript، والخادم Express يدعم Supabase PostgreSQL أو SQLite المحلية. لا توجد حسابات أو مستندات تجريبية في قاعدة التشغيل.

## التشغيل

يتطلب إصدار Node.js 22 حديثًا. استخدم 22.22 أو أحدث ضمن سلسلة 22 لتشغيل اختبارات المتصفح أيضًا. الخادم لا يحتاج Chrome أو واتساب؛ Puppeteer اعتماد تطوير للاختبارات فقط.

```powershell
npm install
npm start
```

افتح `http://localhost:3000/index.html`. عند أول إنشاء مستند أو الضغط على الحساب، أنشئ حساب المالك بكلمة مرور من 12 حرفًا على الأقل. المنصة مخصصة لمالك واحد؛ العميل لا يحتاج حسابًا.

فتح HTML بواسطة `file://` أو رفعه وحده إلى استضافة static لا يشغّل النظام: الدخول، التخزين، التوقيع والمشاركة تحتاج الخادم. جميع المكتبات والخطوط مستضافة محليًا داخل التطبيق.

## GitHub Pages

تمت إضافة بناء للواجهة الثابتة مع التنسيق والخطوط والأيقونات والمكتبات، ومسارات صحيحة تحت `/fa-to-rhtus3dev/`. الأمر `npm run build` ينتج مجلد `dist/` جاهزًا للنشر، ولا ينسخ ملفات البيئة أو قاعدة البيانات أو الخادم أو جلسة واتساب. لا تختَر Hugo؛ المشروع لا يستخدمه.

من **Settings > Pages > Source** اختر **GitHub Actions**. سير العمل `.github/workflows/pages.yml` يبني وينشر الواجهة عند تحديث `main`، باستخدام ملف قفل npm. تبقى ملفات التشغيل الخاصة خارج ملفات النشر.

**GitHub Pages ينشر الواجهة فقط ولا يشغّل Express أو قاعدة البيانات.** ستظهر حالة «خادم التطبيق غير متصل» عند عدم إعداد API خارجي، ولن يتم إرسال بيانات تسجيل دخول إلى Pages أو الادعاء بأن البيانات محفوظة. تشغيل الدخول والمستندات والتوقيع يتطلب نشر الخادم على استضافة Node منفصلة؛ ليست صفحة Pages بديلًا للخادم.

بعد نشر خادم HTTPS متوافق، يمكن تعيين متغير المستودع العام `PAGES_API_BASE_URL` إلى رابط API مثل `https://api.example.com/api`، ثم إعادة تشغيل سير النشر. لا تضع فيه رابط PostgreSQL أو أي مفتاح سري. الخادم الخارجي يحتاج إعداد CORS وOrigin وCookies موثوقًا لنطاق الواجهة؛ إعداد هذا المتغير وحده لا يجهز ذلك. قواعد بيانات Supabase ومفاتيحها تبقى في الخادم ولا تنشر إلى المتصفح.

يتحدد مسار المستودع تلقائيًا من `GITHUB_REPOSITORY`. عند استخدام نطاق مخصص أو موقع حساب مثل `user.github.io`، عيّن متغير المستودع `PAGES_BASE_PATH` إلى `/`. محليًا يمكن اختباره بمتغير البيئة نفسه. يوجد ملف `404.html` لعرض واجهة روابط `/sign/...`، لكن قبول التوقيع ما زال يتطلب خادم API.

## الخادم العام على Vercel

أُلغي ربط واتساب والإرسال التلقائي. اعتماد العميل وتوقيعه وتنزيل صورة الفاتورة من المتصفح تبقى متاحة. لم تُحذف ملفات التشغيل الخاصة القديمة داخل `data/`.

التطبيق مجهز لتشغيل Express والواجهة على نطاق HTTPS واحد. يحدد `vercel.json` إطار Express وأمر `npm run build:vercel` بدل Hugo. البناء يضع الواجهة والخطوط والمكتبات فقط في `public/`؛ لا ينشر ملفات البيئة أو قواعد البيانات. يعتمد الخادم العام على PostgreSQL خارجي ومفتاح تشفير ثابت، ولا يرجع إلى SQLite عند نقص الإعدادات. إعداد GitHub Pages السابق مستقل ولم يتغير.

1. إذا كُشفت كلمة مرور قاعدة البيانات أو مفاتيح سرية، غيّر كلمة المرور وألغِ المفاتيح المكشوفة قبل النشر. أدخل البدائل مباشرة في جهازك أو لوحة الاستضافة؛ لا ترسلها في المحادثة.
2. تأكد أن حساب المالك موجود في **نفس قاعدة Supabase** من التشغيل المحلي. إنشاء حساب المالك محظور عبر Vercel حتى لا يستولي أول زائر على المنصة. لا تعِد إنشاء المخطط أو تنقل البيانات إلى مشروع جديد إن كنت تريد الاحتفاظ بالمستندات الحالية.
3. بعد رفع تغييرات المشروع إلى GitHub، استورد المستودع في Vercel أو أعد نشر المشروع الموجود. استخدم جذر المشروع `.` وNode.js `22.x`. ملف الإعداد يتجاوز اختيار Hugo القديم؛ لا تستخدم أمر `npx hugo` أو مجلد `dist` هنا.
4. من **Settings > Environment Variables** أدخل `DATABASE_PROVIDER=supabase`، و`DATABASE_URL` لرابط Session pooler على 5432، و`LINK_ENCRYPTION_KEY` بالقيمة الحالية نفسها، و`NODE_ENV=production`. إن كان اتصالك يستخدم شهادة CA، اضبط `DATABASE_CA_CERT_PATH=database/prod-ca-2021.crt`؛ الشهادة العامة مضمّنة في حزمة الخادم.
5. لا تولد مفتاح تشفير مختلفًا أثناء النقل. إذا كان المفتاح المحلي مخزنًا كملف `data/link.key`، انقل تمثيله hexadecimal إلى مدير الأسرار بأداة محلية موثوقة دون نشره. تغيير المفتاح يمنع استرجاع الروابط القديمة من لوحة المالك. لا يحتاج التطبيق مفتاح Supabase secret أو service_role في المتصفح.
6. أعد النشر بعد حفظ المتغيرات. تحقق من `/api/health` و`/api/session`، ثم سجّل الدخول وافتح رابط توقيع من جهاز آخر. نقص الإعدادات أو تعذر اتصال القاعدة يعطي 503 برسالة عامة، وليس نجاحًا وهميًا. لا يكفي ظهور الصفحة لإثبات عمل التخزين والتوقيع.

Vercel Hobby مخصص للاستخدام الشخصي غير التجاري؛ راجع الخطة المناسبة قبل تشغيل فواتير عمل تجاري. حدود الطلبات داخل العملية لا تُشارك بين نسخ Serverless، لذلك اضبط حماية وحدود طلبات إضافية على منصة الاستضافة عند الاستخدام العام. إتاحة نشر فعلي تحتاج دخول حساب Vercel وضبط أسراره؛ تجهيز الكود واختباره محليًا ليس نشرًا عامًا بحد ذاته.

## إعداد Supabase

1. أنشئ مشروع Supabase وافتح **SQL Editor**، ثم شغّل محتوى `database/schema.postgres.sql`. الجداول موجودة في schema باسم `tus3dev`، وليس `public`؛ يمكن اختيارها من Table Editor بعد اختيار هذا الـ schema. لا تضفه إلى Exposed Schemas، ولا تعطّل RLS.
2. من زر **Connect** اختر رابط PostgreSQL من نوع **Session pooler** على المنفذ **5432**. هذا الخيار مناسب للاتصال من Windows والشبكات IPv4. لا تستخدم Transaction pooler على 6543؛ محول الاتصال يستخدم إعدادات الجلسة واتصالًا ثابتًا داخل المعاملة.
3. ملف `.env` جاهز محليًا وغير مضاف إلى Git. ضع رابط الاتصال الكامل في `DATABASE_URL`، مع إدخال كلمة مرور قاعدة البيانات محليًا فقط. إذا احتوت كلمة المرور على رموز خاصة، يجب ترميزها داخل URI. لا ترسل الرابط المتضمن كلمة المرور في المحادثة.
4. اترك `config.json` على `"apiBaseUrl": "/api"`: الواجهة تتصل بخادم المنصة، والخادم يتصل بقاعدة Supabase. لا يحتاج هذا الربط إلى `anon` أو `service_role` داخل المتصفح.
5. أعد تشغيل `npm start`. عندما يكون `DATABASE_URL` غير فارغ يستخدم الخادم Supabase تلقائيًا ويظهر `(postgres)` في رسالة التشغيل؛ إن كانت بيانات الاتصال خاطئة يتوقف دون الرجوع إلى SQLite. يجب أن يعمل رابط الاتصال بحساب قاعدة البيانات `postgres` الذي يملك schema المنشأ في SQL Editor؛ الأدوار العامة بلا سياسات RLS لن تستطيع كتابة البيانات.
6. أنشئ حساب المالك من الواجهة. الحساب والجلسات والمستندات والتوقيعات والدفعات وسجل الأحداث تُحفظ في Supabase. دخول المنصة ما زال يستخدم جلسات الخادم وscrypt؛ ليس Supabase Auth، ولا تُنشأ حسابات داخل `auth.users`.

مثال توضيحي للرابط، لا تُدخل القيم التالية كما هي:

```dotenv
DATABASE_URL=postgresql://postgres.PROJECT_REF:YOUR_DATABASE_PASSWORD@YOUR_SESSION_POOLER_HOST:5432/postgres
```

الملف `.env.example` يحتوي إعدادات نشر Supabase مع `DATABASE_PROVIDER=supabase` الصريح. عند عدم تعيين هذا المتغير محليًا، `DATABASE_URL` الفارغ يعني SQLite، وتعبئته تعني Supabase. بيانات الاتصال الفعلية خاصة وتبقى خارج Git؛ Vercel لا يسمح بقاعدة SQLite.

الاتصال يستخدم TLS مع التحقق من شهادة الخادم. إن طلب الاتصال شهادة CA خاصة، حمّلها من Supabase وضع مسار الملف في `DATABASE_CA_CERT_PATH`. لا تعطّل التحقق من TLS لحل خطأ الشهادة.

قبل نشر Supabase في وضع `NODE_ENV=production` يجب تعيين `LINK_ENCRYPTION_KEY` إلى مفتاح عشوائي ثابت من 32 بايت ممثل بـ 64 حرفًا hexadecimal، وحفظه في مدير الأسرار. أثناء التطوير يُستخدم ملف `data/link.key` إن لم يُحدد المتغير؛ احتفظ بالمفتاح نفسه عند الانتقال للنشر حتى تظل الروابط القديمة قابلة للاسترجاع. لا تشارك المفتاح أو ملف `.env` أو كلمة مرور قاعدة البيانات.

المحول يتحقق من وجود المخطط قبل الاستماع للطلبات محليًا، وقبل معالجة API على Vercel، ويحافظ على معاملة واحدة لكل عملية تغيير مع قفل PostgreSQL يمنع تكرار رقم المستند أو قبول توقيعين متزامنين. SQL لا ينقل بيانات SQLite تلقائيًا؛ قاعدة Supabase تبدأ فارغة ما لم تنفذ ترحيل بيانات منفصلًا. الاختبارات الآلية تستخدم PostgreSQL مضمّنًا مع المحول نفسه ومسارات API نفسها ولا تستخدم أسرار قاعدة التشغيل.

## المسار المنفذ

- لوحة تحكم فارغة في البداية، إحصائيات حقيقية مع اختيار العملة، وبحث وتصفية وترقيم صفحات.
- سبعة أنواع مستندات؛ بيانات الطرفين، الخدمات، الخصومات، حسابات البنك والإقرار والملاحظات.
- معاينة فورية؛ النموذج يسارًا والمعاينة يمينًا على الكمبيوتر، وزر معاينة على الجوال.
- حفظ تلقائي في الخادم مع رقم إصدار يمنع الكتابة فوق تحديثات نافذة أخرى.
- دفعات يدوية أو 50/50 أو 30/40/30، ودعم الدفع الجزئي مع مبلغ مدفوع فعلي.
- روابط عشوائية من 256 بت، انتهاء اختياري، إلغاء الرابط أو إعادة توليده؛ لا تتضمن معرف المستند الداخلي.
- صفحة عميل للقراءة فقط؛ موافقة وتوقيع بالماوس/اللمس، تراجع وإعادة ومسح، وتثبيت التوقيع قبل التأكيد النهائي.
- رفض التوقيع الفارغ في الواجهة والخادم، وفك صورة PNG والتحقق من بكسلاتها باستخدام sharp.
- اعتماد ذري يحفظ التوقيع ووقت الاعتماد ونسخة المحتوى وبصمة SHA-256 وسجل الأحداث وUser Agent.
- قفل المحتوى منذ الإرسال؛ يمكن إلغاء رابط غير معتمد لإعادة المسودة. النسخة المعتمدة لا تتغير؛ التعديل ينشئ Revision جديدًا بلا توقيع أو رابط موروث.
- حماية إضافية في SQLite وPostgreSQL ضد تحديث المحتوى المعتمد والتوقيعات ونسخ المحتوى وأحداث السجل.
- عرض السجل، أرشفة واستعادة، إنشاء نسخة، طباعة، وتنزيل PNG/JPG بدقة 3× بعد الاعتماد.
- صفحات العملاء والإعدادات، هوية وشعار قابلان للحفظ، حسابات بنكية متعددة ونصوص إقرار لكل نوع.
- تحديث الحالة والإشعارات داخل اللوحة كل 15 ثانية حين تكون الصفحة نشطة؛ لا يوجد إرسال بريد إلكتروني.
- وضع فاتح/داكن، خطوط عربية محلية، Skeleton، حالات فارغة، تنبيهات ونوافذ تأكيد.

الإحصائيات المالية تستخدم أحدث نسخة غير ملغية/مرفوضة لكل رقم مستند لتجنب تكرار مبالغ المراجعات؛ لا تجمع عملات مختلفة. تحديث تقسيم الدفعات بعد تغيير قيمة الخدمات يحتاج إعادة اختيار التقسيم أو تعديل المبالغ يدويًا. المبلغ «المدفوع» سجل يدوي، وليس اتصالًا مصرفيًا أو بوابة دفع.

## التخزين

### ملفات SQL وإعداد API

- `database/schema.sqlite.sql`: السكربت المستخدم عند تشغيل وضع SQLite المحلي، مع الجداول والعلاقات والفهارس وحماية المحتوى المعتمد. يمكن تشغيله في أداة SQLite على قاعدة فارغة، وإعادة تشغيله لا تحذف البيانات. إنشاء الحساب يتم من المنصة، وليس بكتابة كلمة مرور داخل SQL.
- `database/schema.postgres.sql`: سكربت PostgreSQL 14+ صالح أيضًا للتنفيذ في Supabase SQL Editor. ينشئ الجداول داخل schema خاص باسم `tus3dev` ويستخدم JSONB وTIMESTAMPTZ وRLS. لا يفتح البيانات للمتصفح ولا يضيف حسابات تجريبية. اختُبر باستخدام PostgreSQL مضمّن عبر PGlite.
- الملف الثاني يجهّز قاعدة PostgreSQL؛ الربط بالخادم منفذ عبر `database/store.js` و`DATABASE_URL`. لا ينقل بيانات SQLite ولا ينشئ Supabase Auth أو REST API للمتصفح.

مكان رابط API هو `config.json`:

```json
{
	"apiBaseUrl": "/api"
}
```

اترك `/api` لاستخدام الخادم الحالي، أو ضع رابط خادم خاص متوافق مع المسارات والاستجابات الحالية، مثل `https://api.example.com/api`. أعد تشغيل `npm start` بعد تعديل الملف؛ يقرأ الخادم الإعداد ويجهز سياسة CSP للنطاق المحدد. يشغّل `index.html` إعداد الاتصال قبل الواجهة، وجميع طلباتها تستخدم هذا الرابط مع Cookies.

الرابط ليس مفتاح API. محتوى الإعداد عام: لا تضع فيه كلمة مرور قاعدة البيانات أو `service_role` أو أي مفتاح سري، ولا ترسلها في المحادثة. بيانات الاتصال الخاصة توضع في `.env` أو مدير أسرار الخادم. مشاركة اسم الخدمة وعنوان المشروع غير السري تكفي للمساعدة في الإعداد.

لا تستخدم عنوان Supabase `/rest/v1` أو publishable/anon key مكان رابط الخادم مباشرة؛ الواجهة تتوقع `/session` و`/login` و`/documents` و`/sign/:token` وغيرها، وهي مختلفة عن Supabase REST. الجداول الحساسة في PostgreSQL خاصة وRLS بلا سياسات عامة عن قصد؛ تهيئة صلاحيات الخادم والتحقق من المالك ضرورية، ولا يجب تعطيل RLS لإجبار الواجهة على الوصول.

لخادم API على نطاق آخر، يجب أن يسمح بـ CORS لنطاق الواجهة المحدد، و`Access-Control-Allow-Credentials: true` والهيدرين `Content-Type` و`X-CSRF-Token`. ينبغي استخدام نفس الموقع عبر reverse proxy أو نطاقات فرعية موثوقة للجلسات؛ مشاركة Cookies بين مواقع مختلفة قد تُحظر في المتصفح وتحتاج إعدادًا أمنيًا مستقلًا. لم تتم تهيئة خدمة خارجية أو الاتصال بها بعد.

في وضع SQLite يُنشأ مجلد `data/` ويحتوي على قاعدة `tus3dev.sqlite` ومفتاح `link.key`. في وضع Supabase تُحفظ الجداول في PostgreSQL؛ أثناء التطوير قد يبقى المفتاح في `data/link.key`، وفي الإنتاج يؤخذ من `LINK_ENCRYPTION_KEY`. لا ترفع أيًا من الأسرار إلى Git أو مجلد عام. المفتاح يشفر الرموز المحفوظة حتى يستطيع المالك نسخ الرابط لاحقًا. فقدانه يمنع استرجاع الروابط الحالية للمالك.

الجداول: `users`, `sessions`, `clients`, `documents`, `document_items`, `payments`, `bank_accounts`, `settings`, `signatures`, `document_links`, `document_events`, `document_revisions`. العلاقات تستخدم Foreign Keys، والبحث والمالك والحالة والأحداث وروابط المستند مفهرسة. المحتوى القانوني يُحفظ كنسخة JSON ثابتة بالإضافة إلى صفوف الخدمات والدفعات المرتبطة.

تُخزّن التواريخ بالتوقيت UTC وتُعرض حسب توقيت جهاز المشاهد. لا تُخزّن عناوين IP حاليًا. روابط الاعتماد بيانات سرية لحاملها؛ من يملك الرابط يستطيع الاعتماد باسم العميل. الرسم الإلكتروني وحده ليس تحققًا موثقًا من الهوية ولا شهادة توقيع رقمي قانونية.

## الأمان والنشر

هذه نسخة تشغيلية مختبرة محليًا، وليست شهادة جاهزية إنتاجية أو اعتمادًا قانونيًا. قبل استخدامها مع عملاء فعليين:

1. أنشئ حساب المالك محليًا قبل إتاحة الخادم للعامة، لمنع استيلاء أول زائر على إعداد الحساب.
2. انشر خادم Node مع إعداد الاتصال السري بـ Supabase ومفتاح تشفير ثابت. في وضع SQLite المحلي يلزم قرص دائم؛ لا تستخدم تخزينًا مؤقتًا/Serverless لملف SQLite.
3. ضع reverse proxy مثل Caddy أو nginx أمام التطبيق واضبط نطاقك وHTTPS. استخدم `NODE_ENV=production` لتفعيل Secure Cookies. فعّل `TRUST_PROXY=1` فقط خلف proxy موثوق واحد؛ التطبيق يستمع على `127.0.0.1` افتراضيًا.
4. امنع الوصول المباشر إلى منفذ Node، وحدّث الاعتماديات دوريًا، واضبط حدود الطلبات على الـ proxy أيضًا. Rate limiting الحالي داخل عملية Node ومخصص لتشغيل نسخة خادم واحدة.
5. احمِ قاعدة البيانات والمفتاح بصلاحيات النظام وACL على Windows؛ تشفير الرموز لا يعني تشفير جميع بيانات العملاء أو النسخ الاحتياطية.
6. في Supabase جهّز نسخًا احتياطية للـ schema المخصص واختبر الاستعادة، واحفظ مفتاح التشفير بشكل مستقل. في SQLite انسخ مجلد `data/` كاملًا بعد إيقاف الخادم لإجراء نسخة احتياطية متسقة؛ لا تنسخ ملف SQLite وحده أثناء عمل WAL.
7. أضف سياسة خصوصية واحتفاظ بالبيانات ومراجعة قانونية لنصوص الإقرار. أضف OTP/تحقق هوية إذا كانت طبيعة الاتفاق تتطلبه.
8. نفّذ مراقبة وتشغيلًا كخدمة ونسخًا احتياطية واختبار تحميل ومراجعة أمنية قبل وصف النشر بأنه Production Ready.

المنفذ البديل في PowerShell:

```powershell
$env:PORT = "3002"
npm start
```

كلمات المرور مشتقة باستخدام scrypt مع salt عشوائي؛ الجلسات في قاعدة البيانات المختارة، وCookies من نوع HttpOnly/SameSite Strict. طلبات المالك المتغيرة تتطلب CSRF token؛ الروابط العامة تعتمد bearer token مع تحقق Origin. تستخدم الاستعلامات المعلّمة بالمعاملات والتحقق Zod، مع CSP وHelmet وترميز النصوص قبل عرضها. لا تعرض المسارات العامة ملفات الخادم أو قاعدة البيانات أو `.env`.

## حدود معروفة

- PDF المباشر وOTP ورسائل البريد والتوقيع الافتراضي لمقدم الخدمة غير منفذة. الطباعة متاحة، ويمكن للمتصفح الحفظ كـ PDF، لكنها ليست خدمة توليد PDF مستقلة.
- لا يوجد استعادة كلمة مرور أو تغيير بريد تسجيل الدخول في الواجهة؛ بريد التواصل في الإعدادات مستقل عن بريد الحساب. يلزم تصميم مسار استعادة آمن قبل نشر عام طويل الأمد.
- لوحة التوقيع تحتاج استخدام المؤشر/اللمس؛ أدواتها قابلة للاستخدام بلوحة المفاتيح، لكن يلزم بديل توقيع مناسب لمن لا يستطيع الرسم، حسب متطلبات الإتاحة لديك.
- التصدير صورة طويلة بعرض A4 عند زيادة الصفوف؛ لا يقسم المستند الطويل إلى صفحات صور منفصلة. قد تختلف حدود أبعاد Canvas حسب المتصفح.
- توجد حدود موارد: 500 خدمة، 100 دفعة، 30 حسابًا بنكيًا، وصورة شعار حتى 1 MB؛ إضافة الصفوف ديناميكية وليست بيانات ثابتة.
- أوقات المشاهدة تسجل أول فتح نشط للرابط. الحالات Signed ثم Approved محفوظة كأحداث في معاملة واحدة؛ الحالة النهائية Approved.

```powershell

```

الاختبارات تستخدم SQLite في الذاكرة وPostgreSQL مضمّنًا عبر PGlite، ولا تتصل بمشروع Supabase أو تضيف بيانات إلى قاعدة التشغيل. تغطي الجلسات وCSRF، الحسابات، التحقق، الحفظ بإصدارات، الدفعات، الرموز وإلغائها وتجديدها، انتهاء الصلاحية، الموافقة والرفض، التوقيع الفارغ، النسخة الثابتة وقفلها، المراجعات والأرشفة والإعدادات وعدم كشف الملفات الخاصة. تشمل اختبار المسار الكامل عبر محول PostgreSQL، والتراجع عن المعاملات، وكتابات متزامنة، وقبول توقيع واحد فقط عند الطلبات المتزامنة. تم أيضًا اختبار الواجهة على الكمبيوتر والجوال وتصدير PNG/JPG.
